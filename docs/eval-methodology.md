# 评估方法

目标不是证明系统「能用」，而是回答三个问题：每一层（混合检索、重排、版本过滤）各自带来多少收益？错误主要出在检索还是生成？这些结论在题量有限时有多可信？

## 1. 题库构成

默认分层（`scripts/build_eval_set.py --per-type`）：

| 题型 | 数量 | 构造方式 | 考察点 |
| --- | --- | --- | --- |
| 事实查找 fact | 19 | 从单个 chunk 生成有唯一答案的问题 | 基础召回与生成 |
| 表格查询 table | 12 | 从含 markdown 表格的 chunk 生成数值题 | 表格切分与数值保真 |
| 跨文档 cross_doc | 9 | 同时引用两份文档 | 多路召回、答案整合 |
| 版本陷阱 version | 0 | 只接受同 `doc_no` 的两份文档配对 | 版本过滤是否选对现行版 |
| 不可答 unanswerable | 10 | 询问语料未收录的城市、厂商或制度 | 拒答能力 |

共 50 题。题目与 gold 由 DeepSeek 生成，生成结果写入 `eval/questions.jsonl` 后**人工校对**：首轮 20 题，余力再补到 40 题；`EvalQuestion.verified` 标记是否已校对，报告按 verified / unverified / all 分组给出指标，避免未校对题目把结论抬高。

两处与「凑数量」有关的取舍：

- **version 题为 0。** 公开语料里没有同一文号的新旧版本对。早期版本用「同类文档」凑配，生成的其实是不相关的两份文件之间的对比题，会把版本过滤这一栏的指标算成噪声，因此改成凑不出就返回空。版本过滤目前只由单元测试覆盖，报告中不单列该题型。
- **不可答题先自动筛一遍。** 生成器容易产出「主题相关但语料里其实有答案」的题（例如问充电桩配比，而语料恰好写了）。`screen_unanswerable` 对每题取 BM25 前 5 段交给模型判断能否直接回答，能答的丢弃；判定无法解析时保留该题。筛选只是初筛，人工校对仍是最终标准。

## 2. gold 如何锚定

`GoldSpan(doc_id, char_start, char_end, quote)`，字符区间相对于解析后的文档全文。

- 切分参数变化不影响标注有效性；评估时用 `resolve_gold_chunks` 找出与区间重叠的 chunk 作为 gold 集合。
- 若某题的区间在当次切分中找不到任何 chunk，该题记为「评估集问题」，不参与检索均值，并在失败案例里单列。
- 不可答题的 gold 为空，只参与拒答准确率。

## 3. 指标定义

设 `G` 为 gold chunk 集合，`R_k` 为检索返回的前 k 个 chunk。

| 指标 | 定义 |
| --- | --- |
| Recall@k | `|R_k ∩ G| / |G|` |
| MRR@10 | 第一个命中位置的倒数排名；未命中为 0 |
| nDCG@5 | `DCG@5 / IDCG@5`，折损 `1/log2(rank+2)`，二值相关性 |
| 引用精确率(strict) | 答案引用的 chunk 中落在 gold 区间内的比例；gold 单锚，跨文档引用会被判错，只作下界 |
| 引用精确率(claim) | judge 逐条判断「该引用是否直接支撑对应陈述」，取判定为真的比例 |
| 引用召回率 | gold chunk 被引用的比例 |
| 答案正确率 | judge 判为 `correct` 的比例（`partial` 单列） |
| Faithfulness | judge 判定答案中事实均可由上下文支撑的比例 |
| 拒答准确率 | `abstained` 与「是否为不可答题」一致的比例 |

统计口径：

- 检索与引用指标只在**有 gold 的可答题**上取均值；不可答题计入会把 Recall 人为拉低。
- 答案正确率 / Faithfulness / 拒答准确率统计全部题目。
- 括号内为 bootstrap 95% 置信区间：1000 次重采样，固定 seed=0，取 2.5% / 97.5% 分位。

每组跑同一批题目、同一个生成模型与 judge。报告同时给出总表、分题型表与失败案例。

## 5. Judge

- 模型：SiliconFlow 上的 Qwen2.5-72B（`JUDGE_MODEL`），与生成模型 DeepSeek 异源。报告与 README 中的数字均出自这一版。
- **同源对照**：2026-10-27 首轮因硅基流动余额为 0，judge 临时指向 DeepSeek 自判。充值后按跨家族配置重跑，缓存键包含模型名，换 Qwen 后重新判定、未复用同源结果。
- 两版判定的逐题对比：200 组（4 配置 × 50 题）中 **189 组一致，94.5%**。11 处分歧为 wrong→partial 5、correct→partial 4、wrong→correct 1、partial→correct 1，集中在「正确 / 部分正确」的边界，没有出现「正确 ↔ 错误」的系统性翻转。
- 净效应：重排配置的答案正确率从 0.760（DeepSeek 判）降到 0.740（Qwen 判），即同源裁判整体略宽松，但幅度在 50 题置信区间内，不足以单独下结论——它只说明「同源偏乐观」的方向成立，大小无法从这一组数据估准。
- 输出严格 JSON：`correct`（correct / partial / wrong）、`faithful`、`citations`（逐条引用的 precise 判定与理由）、`reason`。
- **逐条引用判定**：`citations` 必须与答案引用条数一致，哪怕答案是「无法判断」。首版提示词没写这一条，实测有 6 条引用的答案返回空数组，等于把引用最多的那批答案排除在分母外——补上后覆盖率恢复 100%。
- 解析失败或档位不在枚举内一律按 `wrong` 记录并写明原因，不做猜测映射——宁可少算，不要不可审计。
- 偏差控制：保留全部判定理由；跨家族一致率见上。judge 与**人工**的一致率尚未测量（20 题人工校对只核对了 gold，没有逐条复核 judge 的 correct/partial/wrong 档位），这是当前生成类指标最大的未验证环节。

## 6. 错误分类

每题只记一个主因，优先级：

`评估集问题` → `召回缺失` → `拒答错误` → `版本混淆`（仅 version 题）/ `生成错误` → `生成幻觉`。

单主因便于聚合计数；完整信号（检索排名、gold、判定理由、答案）都保留在 run record 里，需要多因分析时可重新归类。

## 7. 可复现契约

- 原始语料不入库（`corpus/*` 除来源清单与词典外均 gitignore）。
- `eval/questions.jsonl`、`eval/judge_verdicts.jsonl`、`reports/eval_report.md` 入库。
- `judge_verdicts.jsonl` 每条记录包含完整 run record（检索排名、gold、各项指标、判定），
  `python scripts/eval.py --report-only` 可在不联网、无 API key 的情况下重算并重写报告。
- 所有模型调用按内容哈希缓存，重跑同一批问题不会产生新的 API 调用。

## 8. 已知局限

- 题目由 LLM 生成，倾向「好问、好答」，指标可能偏乐观；靠人工校对与不可答题缓解，无法完全消除。
- 50 题的置信区间较宽，配置之间 2–3 个百分点的差距不足以支撑结论；报告中所有对比都附区间，跨区间才下判断。
- `version` 题型缺席，版本过滤的收益只能靠单元测试与 `full` 配置的整体表现间接体现。
- `cross_doc` 题的 gold 只锚定生成时引用的那一段，所以跨文档题实际只要求召回其中一份文档；真正的多路召回能力被低估，这部分由人工失败案例分析补充。同一个缺陷让 strict 引用精确率在跨文档题上封顶 0.5——9 道题撑不起 0.90，这也是新增 claim 口径的直接原因（详见 §5）。
- judge 与人工的一致性尚未量化。跨家族裁判消除了「同源偏袒」，但不等于判定正确；本次报告中的生成类指标仍应视为「judge 视角」的数字。
