# 演示验收：10 个真实业务问题端到端

日期 2026-10-28。验收方式：`scripts/serve.py` 起真实服务（uvicorn，CPU），用 10 个停车业务问题直接打 `POST /chat`，逐题核对答案正确性、是否拒答、引用是否指向能支撑答案的原文。

- 服务：`HF_HUB_OFFLINE=1 python scripts/serve.py --device cpu --port 8010`
- 脚本：逐题 POST，结果落盘 `demo_results.jsonl`（原始答案与引用全文）
- 语料：9 份文档 / 513 chunks
- 延迟：中位 11.5 s，最长 19.8 s（CPU 推理 bge-m3 + reranker + DeepSeek）

## 结论

| # | 问题 | 判定 | 说明 |
| --- | --- | --- | --- |
| 1 | 湖南办法规定哪些车辆免收停车服务费 | ✅ | 完整列出第十九条七类情形，引用湖南办法 p.3 |
| 2 | 停车场应在何处公示收费标准 | ✅ | 合并两份文档：运营规范「出入口处明示」+ 湖南办法第二十三条「入口处和交费处」 |
| 3 | 湖北与湖南对免费停放时长是否一致 | ✅ | 结论「不一致」正确，分别引两省条文 |
| 4 | 客服中心接到投诉的处理流程 | ✅ | 安抚 → 工单记录 → 转交部门 → 1~3 工作日反馈 → 回访 |
| 5 | 大华系统如何统计某车场每日收入 | ❌ 误拒 | 语料有（p.80 Report Statistics），检索未召回 |
| 6 | 停车场车辆丢失，经营者是否赔偿 | ✅ 正确拒答 | 语料确无赔偿条款，全库 `赔偿`/`丢失` 命中 0 |
| 7 | 大华系统如何添加操作员账号 | ❌ 误拒 | 语料有（p.50 3.6.4 User Management），检索未召回 |
| 8 | 运营管理规范对夜间照明的要求 | ⚠️ 部分 | 拒答，但先给出语料内的照明要求（≥30 lux / 车位 ≥20 lux）并说明「未专门规定夜间」 |
| 9 | 北京市条例对路侧电子收费的规定 | ✅ 正确拒答 | 全库 `北京` 仅命中出版信息，条例未收录 |
| 10 | 停车场充电桩数量配比要求 | ✅ | 运营规范 5.6.1「配建或预留比例不少于 10%」 |

- 不可答题 2 题：拒答 2/2。
- 可答题 8 题：直接答对 6 题（Q1–Q4、Q10 完整，Q8 部分但诚实），误拒 2 题 → **可答误拒 25%**。
- 与自动评估方向一致：评估集可答误拒 17.5%（7/40）。本组只有 8 道可答题，25% 的置信区间很宽，量级相符即可。

## 两个误拒的根因：不是语料缺失，是跨语言检索

初步判断曾怀疑「大华手册正文没入库」，复核后**不成立**：

```
$ grep 大华 chunks: 278 个
User Management   → p.50  Basic Configuration 3.6 > 3.6.4 User Management（正文有「Add User」界面）
Report Statistics → p.80  Report Statistics 3.8 > 3.8.1 Charge Detail / 3.8.3 Shift Statistics
```

真正的差异是**语言**：湖南/湖北办法、运营规范、广东指南都是中文，大华手册是**英文**。问句用中文业务词汇，手册标题是英文，中间没有词面交集。

检索链路逐级排在下面的位置（dense top-50 / sparse top-50 / RRF 融合池 20 条）：

| 目标 chunk | dense | sparse | 融合池 |
| --- | --- | --- | --- |
| Q7 → p.50 User Management | 36 | 未命中 | 未进入 |
| Q5 → p.80 Report Statistics | 未进 top-50 | 未命中 | 未进入 |

两点值得记下：

1. **文档级跨语言是通的，段落级不是。** Q7 的 dense top-8 全部来自大华手册——模型准确地把中文问题对到了英文手册，只是选错了段落：`Add vehicle owner` / `Add parking card` / `Add cards in batches` 全都因为共享一个 "Add" 而排在 `User Management` 前面。Q5 更远，最接近的只有 p.81 `Information Search`（dense 第 7）。
2. **融合池宽度是硬约束。** 正确 chunk 在大华手册里 dense 排 36、sparse 完全不命中，RRF 得分只来自单一通道，进不了前 20 的融合池，因此**重排根本没有机会看到它**。把 `rerank_top_k` 调大无用，`fused_top_k` 才是要动的那个。

对照 Q5/Q7 与答对的 8 题可以确认这不是「拒答阈值过严」：Q1–Q4、Q10 都是单语中文语料，检索直接命中；两条误拒全部落在中↔英的文档上。

## 验收顺带发现的真实缺陷

**API 的 `/chat` 在 uvicorn 下从未真正跑通。** 首次手工验收时全部请求 500：

```
sqlite3.ProgrammingError: SQLite objects created in a thread can only be used in that same thread.
```

FastAPI 把同步端点丢进线程池执行，而 `ChunkStore` 的连接是在主线程建的。TestClient 默认同线程调用，所以 130 个测试全绿、缺陷一直没暴露——这正是「手工端到端验收」相对自动化测试的增量价值。

修复（`src/parking_kb/index/store.py`）：连接改为 `check_same_thread=False`，并用 `RLock` 串行化全部访问；回归测试 `test_store_is_usable_from_another_thread` 先在旧代码上复现同一异常，再转绿。

## 引用可点开原文

前端每次回答附带每条引用的 `doc_id / title / section_path / page_start / text`，`/chat` 响应的 `citations` 与 `[n]` 编号一一对应，点击可展开原文段落。本组 10 题共 12 条引用，抽查全部指向能支撑对应陈述的段落。

一个容易误判的例子：Q10 的引用预览前 110 字是无障碍停车泊位内容，看起来像引错——实际该 chunk 内同时含 5.5.3 与 5.6.1 两节，`配建或预留比例应不少于10%` 就在同一段里。切分重叠 100 字符也会让同一句话出现在相邻两个 chunk 中，所以「同一结论被引两次」多数是合法的重叠，不是重复引用。

## 复核（同日，跨语言检索改动之后）

给英文 chunk 加了中文检索描述并重建索引后重跑这 10 题：

- **Q5、Q7 仍然拒答。** 变化是引用里出现了正确的章节（`Report Statistics 3.8`、`3.6.4 User Management`），说明检索从「完全打不中」变成「打中章节」；但拿到的是参数表而非 p.50 的「Add User」操作步骤，模型仍判证据不足。
- 只有在把融合池放宽到 50/50/40 时，这两题的目标段落才进入最终 top-8，可答案质量没有实质变化，而检索耗时从 11.4 s 涨到 26.8 s、Recall@5 不变、MRR/nDCG 略降，因此没有采纳（ADR-010）。

结论：这两个误拒的根因是**跨语言 + 段落级语义**，单靠描述或放宽漏斗都不够；真正对症的是查询侧中→英改写或段落级人工对齐，留作后续。

## 再复核（同日，表格抽取修复之后）

Q5 的目标（`3.8 Report Statistics`）本身是表格页。PDF 表格此前有两个抽取缺陷：单元格丢词间空格、双线边框错列。修好后重建索引（ADR-011），表格切片 Recall@5 从 0.667 升到 0.750，全量 Recall@5 从 0.812 升到 0.863。

**这 10 题没有重跑**，本节上方的判定仍是表格修复之前的结果；生成侧指标同样未更新。要确认 Q5 是否真的不再误拒，需要重跑一次演示或完整评估。

## 后续（按性价比）

1. **查询侧中→英改写**（Q5/Q7 真正对症的修法）：入库侧中文描述已证明能把英文段落变得可检索，但段落级仍选错。查询改写让检索直接落到英文原文上，代价是每次查询多一次模型调用。
2. ~~放宽融合池~~：已实测无收益、延迟 2.4 倍，放弃（ADR-010）。
3. 可答误拒 17.5% → 目标 10%，与评估集 cross_doc 0/9 同源，属同一批「证据分散或跨文档」的题。
